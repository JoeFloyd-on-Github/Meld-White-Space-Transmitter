## NAND health — the reason this unit needed recovery

`nand bad` reports **209 bad erase blocks**, and they are **not** scattered: every
one falls in a single contiguous zone.

- Range: **`0x03600000` .. `0x058e0000`** (~36 MiB, ~280 erase blocks of 128 kB).
- That range is **exactly the `RootFS_1` partition** (`mtd7`, 0x3600000–0x5900000)
  — the **bank B** root filesystem.
- **~75 %** of that partition's blocks are bad; **~5.1 %** of the whole 512 MiB
  device. The rest of the chip (bank A kernel/rootfs, both app partitions, the
  bootloader/env region) shows **no** reported bad blocks.

The full offset list is in
[`../captures/uboot-console-2026-11-22.txt`](../captures/uboot-console-2026-11-22.txt).

## Bank status and the recovery performed

As received, the saved U-Boot env had **`current_active=1`** (bank B). Because
bank B's `RootFS_1` sits on the destroyed NAND region above, the unit **booted but
then hung**:

```
VFS: Mounted root (yaffs filesystem) on device 31:7     (mtdblock7 = RootFS_1)
Freeing unused kernel memory: 192k freed
do_page_fault() #2: sending SIGSEGV to init             -> hang, no shell, no network
```

**Bank A is healthy.** `current_active=0` boots `Linux_Kernel_0` + `RootFS_0`
(`mtdblock6`) with no SIGSEGV, brings up networking, starts `telnetd`, and runs the
AV app.

**Action taken (2026-11-22), with the owner's authorization:** switched the default
bank to A and persisted it —

```
setenv current_active 0
saveenv            # Saving Environment to NAND... Erasing Nand...Writing to Nand... done
```

Verified: on a clean `reset` with no intervention the unit now autoboots bank A to
a working shell. The procedure is the general one in
[`../bootloader.md`](../bootloader.md) §5; this records that it was applied to this
unit and that bank A is the good one here.

## What runs on bank A (this unit)

- Active app: **`av_streamer`** (HDMI input → MPEG, DVO output) from `/disk/Meld/AV30`.
  This bank is the **AV streaming** personality of the box.
- The white-space pieces are present on the rootfs but **not** the active service
  here: `/usr/bin/whitespaceagent` (9.1 MB), `/usr/bin/MeldAgent` (3.1 MB),
  `wsagent_start` / `wsagent_stop`. `MeldAgent` runs once at boot to read the radio
  (reports FCC ID / serial / channel, **TX disabled**).
- `thttpd` web UI on port 80; `telnetd -l /bin/sh` (root, no password) on port 23;
  UPnP/SSDP on 1900 advertising `MELD_BOX_00000601`.

## Network access for this unit

- On bank A, `setipeth0` brings eth0 up at **`172.16.200.39/24`**. If the PC is on a
  different subnet, either add a route / second IP in `172.16.200.0/24`, or set a
  temporary address over the serial shell, e.g.
  `ifconfig eth0 192.168.1.195 netmask 255.255.255.0 up` (**RAM-only**, reverts to
  172.16.200.39 on reboot).
- Telnet root shell and `nc` file transfer as in
  [`../device-access.md`](../device-access.md).

## White-space stand-in installed and transmitting (2026-11-22)

With the owner's authorization and the RF output terminated, the local
SpectrumBridge stand-in `sb_mips` (the 31-channel 21–51 build) was installed on
bank A and the agent drove the radio on the air — the first confirmed white-space
transmit on this unit.

- **Reachable at `192.168.1.195`** this session (telnet root shell as usual).
- **Install (all on bank-A rootfs, survives reboot):** `sb_mips` + the `sb_start`
  supervisor in `/usr/bin`; `/etc/hosts` redirects `tvws.spectrumbridge.com` →
  `127.0.0.1`; the boot hook `/usr/bin/sb_start &` is inserted into
  **`/etc/init.d/setipeth0`** just before its `wsagent_start` line. On this
  firmware `rcS` does **not** call `wsagent_start` — `setipeth0` does (`rcS` only
  starts `av_streamer`), so this is the hook point, not `rcS`. Backups left as
  `/etc/hosts.orig` and `/etc/init.d/setipeth0.presb`.
- **Agent protocol (SpectrumBridge v3):** `whitespaceagent` makes a
  `PUT /v3/devices/US/OKVMT300/601` registration, then a
  `GET /v3/channels/US/<lat>/<lon>/`. `sb_mips` answers both `200` /
  `SBI-Status: 0` with the channel list, **unchanged from the non-AV bench unit** —
  so the same stand-in works here even though this unit's agent is a different
  build (**v45**, Dec 2013, vs the repo's v44 — which is why its md5 differs).
- **Transmit requires a live video input.** With no source, `av_streamer` loops
  `NO digital video standard detected` and the transmitter will not key
  (`radio_status 0`) even though registration and channel selection succeed.
  Connect a source → it locks (confirmed **1080i@60**) → **`radio_status 1`**, and
  the web Status page shows *Transmitter: Enabled*, *Operating Channel 31*,
  *Registration/Channel: Success*. (The non-AV unit keys a bare carrier without
  video; the AV video unit does not.)

## Prior open follow-ups — now done

- **Full NAND backup — DONE (2026-11-22).** All 11 MTD partitions (block-level) +
  the live `rootfs`/`/disk` as `cpio` streamed over `nc` to the share under
  `backup-mt300-sn601-v1.38-2026-11-22/` (538 MB, verified). Kept **out of this
  repo** (owner PII + web hash). Procedure:
  [`../device-backup.md`](../device-backup.md). Both `RootFS` slots read back as
  NAND-noisy snapshots at the `mtdblock` layer (no `nanddump`, so no OOB/ECC), so
  the `cpio` archives are the authoritative file-level capture.
- **Web-UI password — DONE.** The factory default (`admin` + a traditional
  DES-crypt hash) is not in common wordlists and is not publicly documented;
  rather than crack it, it was reset to a known value with
  `htpasswd -b /disk/www/.htpasswd admin <pw>` over the root shell (the new value
  lives in the owner's local notes, not in this repo). The original `.htpasswd` is
  preserved in the backup.
