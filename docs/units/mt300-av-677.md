# Unit notes: MT300-AV, serial 677

Facts specific to **one physical unit** (serial `677`). These do **not** generalize
to every MT300 — bad-block maps, MACs, IPs and board quirks are per-unit. The
general bootloader / flash / bank reference is [`../bootloader.md`](../bootloader.md);
the hardware variants are in [`../hardware-versions.md`](../hardware-versions.md);
getting a shell is [`../device-access.md`](../device-access.md).

This unit is the one whose full NAND dump is on the share as
`cpio-mt-300av-sn677-mtdblocks` (see `PROJECT_CONTEXT.md`).

## Bootloader specifics (this unit)

- **U-Boot 1.1.3** (Mar 18 2014), prompt `XCode_Viper#` — see
  [`../bootloader.md`](../bootloader.md) for the general reference.
- **`bootcmd` is hardcoded to bank A**, not the `nboot`/`current_active` form 601
  uses:
  ```
  bootcmd  = nand read 81000000 300000 800000; bootm 81000000
  bootargs = root=/dev/mtdblock6 rw ethaddr=F8:22:85:0B:01:74
  ```
  It loads `Linux_Kernel_0` (`0x300000`, a standard **uImage**, magic `0x27051956`,
  "Mips Linux 2.6.36 Kernel MT300", load `0x8c000000`) and mounts `RootFS_0`
  (`mtdblock6`). `current_active=1` is set in the env but **ignored** because
  `bootcmd` does not consult it.
- **Real Ethernet PHY.** U-Boot `mii info` reports **OUI `0x4700`, Model `0x11`,
  Rev `0x0C`** at all 32 MDIO addresses — an actual PHY ID, unlike unit 601's
  phantom `0x0080`. This likely reflects a different board revision
  (see [`../hardware-versions.md`](../hardware-versions.md)); both are `Board_ID
  0x2F00` MT300-AV.
- Other env: `ipaddr=192.168.1.194`, `gatewayip=192.168.1.254`, `hostname=MT300MKII`
  (U-Boot only; the Linux hostname is `MT300-AV`).

## NAND health — bad bank, but unused here

`nand bad` reports **209 bad erase blocks**, all in one contiguous zone:

- Range **`0x03600000` .. `0x058a0000`**, i.e. **exactly the `RootFS_1` partition**
  (`mtd7`, bank **B**). ~75 % of that partition is bad; the rest of the chip
  (bank-A kernel/rootfs, both app partitions, bootloader/env) shows **no** bad
  blocks.
- **This is the same failure pattern as unit 601** — the bank-B rootfs region is
  destroyed — but here it is **harmless**: this unit's `bootcmd` always boots
  **bank A** (`RootFS_0`/`mtd6`, clean), so it comes up normally and needs **no
  recovery**. Bank B is simply unusable.

The full offset list is in the console capture under [`../captures/`](../captures).

## Full backup (2026-11-22)

A fresh, verified full backup was streamed over `nc` with `tools/backup/` to the
share at **`backup-mt300-sn677-v1.38-2026-11-22/`** (541 MB; all 11 MTD images +
live `rootfs`/`/disk` cpio; owner PII, **out of the repo**). Notes specific to
this unit:

- **Mixed A/B live state.** `root=/dev/mtdblock6` (RootFS_0, bank A) but `/disk`
  is mounted from **`/dev/mtdblock9`** (AppFS_1, bank B) — `actimage` reports image
  1, so `rcS` mounts the bank-B app partition over the bank-A root. The backup
  reads the live partitions from `/proc/cmdline` + the `/disk` mount, so the cpio
  captured the correct active filesystems (rootfs mtd6 = 299 files, `/disk` mtd9 =
  667 files).
- `mtd7` (RootFS_1, the destroyed bank-B rootfs) is a non-reproducible NAND-noise
  snapshot (two device reads differ) — expected, per the block-level caveat; the
  cpio is authoritative for the live filesystems.
- This unit's `fccidSerialInfo` has **no `FCCID:` line**, so the script auto-named
  the dir `backup-meld-…`; it was renamed to `backup-mt300-…` for consistency.
- An `nc` streaming race left `mtd9`/`mtd10` misaligned on the first pass; both
  were re-pulled and now verify exactly, and `backup-meld.sh` was hardened so it
  can't recur (see `meta/verification-notes.txt` in the backup and the pitfall in
  [`../device-backup.md`](../device-backup.md) §6).

`sb_mips` is **not** installed on this unit (pristine OEM firmware).

## White-space stand-in installed and registering (2026-11-22)

With the owner's authorization and the RF output terminated, the local
SpectrumBridge stand-in `sb_mips` (same 31-channel 21–51 build as unit 601,
md5 `c7ed3cca…`) was installed on this unit's bank-A rootfs and is launched at
boot. The agent now registers against it and receives a channel grant; as on
unit 601 the transmitter will not **key** until a live video source is connected
(none attached this session, so `queryInfo` channel selection succeeds but no RF).

**Install (all on the persistent bank-A rootfs; survives reboot):**
`sb_mips` + the `sb_start` supervisor in `/usr/bin`; the boot hook
`/usr/bin/sb_start &` inserted into **`/etc/init.d/setipeth0`** just before its
`wsagent_start` line (as on unit 601 — AV firmware starts the agent from
`setipeth0`, not `rcS`). Backups left as `/etc/hosts.orig`,
`/etc/init.d/setipeth0.presb`, `/etc/config/sbi.presb`. The repeatable recipe is
[`spectrumbridge_spoof_c/device/install_av.sh`](../../spectrumbridge_spoof_c/device/install_av.sh).

**Verified:** across a real power-cycle the boot chain comes up with `sb_mips`
listening on `127.0.0.1:443`, `whitespaceagent` running, and `queryInfo` showing
`TX power = 0x05`, `Channel = 21` (vs `TX disabled` before install) — i.e. a live
`PUT /v3/devices/US/OKVMT300/677` + `GET /v3/channels/US/<lat>/<lon>/`, each
answered `200` / `SBI-Status: 0` with 31 channels.

### Differences from unit 601 / the generic install

Three things on this unit differed from the earlier installs and from the generic
[`install.sh`](../../spectrumbridge_spoof_c/device/install.sh) (which patches
`rcS`). All three are now captured in `install_av.sh`:

1. **The v45 agent connects to the PTR *name* of the resolved host, not the
   dotted quad.** The plain `127.0.0.1 tvws.spectrumbridge.com` redirect (the
   documented Option A, and the v44 `get_ip` in the decompile) was **not enough**
   here: the agent resolved the name to `127.0.0.1`, reverse-looked-up that
   address, got `localhost`, and died printing *"localhost is not a valid IP
   address"* — never opening a socket. Pointing the config straight at `127.0.0.1`
   (Option B) failed the same way. The cure is to make the **first** `/etc/hosts`
   name for `127.0.0.1` a literal dotted quad so the reverse lookup returns a
   valid IP string:

   ```
   127.0.0.1	127.0.0.1 localhost
   127.0.0.1	tvws.spectrumbridge.com
   ```

   With that in place the agent connects and registers immediately. (This is a
   v45-agent behavior; the v44 `get_ip` analyzed in
   [`../on-device-spoof.md`](../on-device-spoof.md) §1 does a clean
   `inet_ntop` and does not need the trick.)

2. **The registration agent was not being started at all.** On AV firmware
   `wsagent_start` only launches `whitespaceagent` when `/etc/config/WSAgentRestart`
   exists; otherwise it runs `MeldAgent -O` (a one-shot radio read that reports
   *TX disabled* and never contacts the database). This pristine unit was never
   registered through the web UI, so that trigger file was absent and `sb_mips`
   saw no traffic. Creating it (`touch /etc/config/WSAgentRestart`, which is what
   the web UI's registration does) puts the unit into the registered,
   agent-running state. Unit 601 already had it (it had been registered).

3. **`/etc/hosts` shipped non-stock.** As received it already redirected
   `tvws` / `vws` / `www.spectrumbridge.com` to a LAN address `192.168.1.248`
   (a previous-owner attempt at a local database redirect; that host is offline).
   It was replaced with the loopback form above. (`/etc/hosts.orig` preserves the
   `.248` version.)

`/etc/config/sbi` `HostAddress` is left as the stock `tvws.spectrumbridge.com`
(the loopback redirect is entirely in `/etc/hosts`), so nothing owner-specific in
`sbi` was changed except that the pre-install copy is saved as `sbi.presb`.

## Virtual channel (PSIP) vs RF channel — a boot-order latch (not fixed)

A receiving TV tuned to this unit displays the program as virtual channel
**`21-1`**, even though the **RF is on channel 31** (verified on a spectrum
analyzer at ~574 MHz, inside ch31's 572–578 MHz band). This is **not** an RF
error — the radio is correctly on the granted channel 31. It is the ATSC
**virtual channel** (the `major-minor` number carried in the transport stream's
PSIP/TVCT) disagreeing with the RF channel, and here that disagreement is
unintended.

**Why 21-1.** The two numbers come from two subsystems that never reconcile:

- `whitespaceagent` negotiates with the database and sets the **RF channel** on
  the NXP radio — the *preferred/granted* channel, **31** (`PreferredChannel` in
  `sbi`).
- `av_streamer` (the ViXS XCode4 front-end) builds the transport stream and its
  PSIP. At startup it reads **`/etc/config/queryInfo`**, takes the `Channel = `
  value, and uses it as the PSIP **`major_channel_number`**; the **minor** is not
  passed by `avs_start.sh` (no `-M`), so it defaults to **1**.

The launcher `avs_start.sh` waits only until `queryInfo` *exists and is
non-empty* — which first happens at the radio's **power-on default channel 21**
(the lowest in the 21–51 grant), *before* `whitespaceagent` moves the radio to
the preferred 31. So `av_streamer` **latches `major = 21` once** and encodes
`21-1`, while the RF later settles on 31. The two never re-sync.

**Confirmed (2026-11-22).** With the RF settled on 31 (`queryInfo` = `Channel =
31`), restarting `av_streamer` via the same `start-stop-daemon` line
`avs_start.sh` uses makes it re-read `queryInfo` and re-stamp the PSIP — a rescan
on the TV then shows **`31-1`**. Video re-locked (1080i@60) and `radio_status`
stayed `1` through the restart.

**Decision: left as-is (not fixed).** A durable fix would be to make
`avs_start.sh` wait until `queryInfo`'s channel equals the granted channel in
`/etc/config/operating` before launching `av_streamer` (or to restart the
streamer once the WS agent has applied the grant). Recorded here as a known
quirk; the general mechanism is in
[`../radio-and-video.md`](../radio-and-video.md).
